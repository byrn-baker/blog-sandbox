# Multi-DC SERVERS internet origination and BORDER1 NAT

The change moves internet origination from a single canary leaf to all nine SERVERS leaves, derives reverse routes and NAT sources from native Nautobot records, and adds a VRF-aware BORDER1 edge. The collection-based EOS templates fix the prior last-value-wins behavior, and local renders produce two defaults plus the expected site prefixes. The current rollout cannot generate that intent as documented because the saved Golden Config GraphQL query is updated only by running the bootstrap job, which the rollout omits. The reverse static also points every workload prefix at the leaf's own anycast SVI address, while the canary tested only traffic sourced from that address.

Watch for: **confirmed** saved-query rollout gap; **likely** workload return forwarding failure through a self next hop; **likely** stale Design Builder roles and tags after policy movement; **confirmed** validation claims that exceed checked-in coverage; **likely** DHCP gateway coupling; **confirmed** config-context ownership contradiction.

**Verdict**: NEEDS_CHANGES

## High-level view

The saved query in Nautobot remains the pre-change query after a repository sync, so generation still lacks device tags, interface roles, parent prefixes, VRF-scoped address-family data, nested endpoint state, and NAT source prefixes until the bootstrap job runs.

Reverse prefix discovery now handles every enabled tagged SVI and emits exact prefix-list entries. The forwarding static uses the SVI's own gateway address as its next hop, and the published canary terminates return traffic on that same local address rather than proving delivery to another host in the subnet.

Design Builder declares the positive role and tag assignments but does not declare their removal when an origin, NAT role, or outside interface moves. The templates then consume any retained native role or tag, which can select an old interface or keep an old leaf originating policy.

The fast and full validation commands pass with the documented counts. They do not assert the new multi-site cases, and Batfish does not parse the new BORDER1 render or model the EOS `egress-vrf` lines.

The outside interface is DHCP-driven while its next hop is a fixed config-context scalar. A lease from another subnet or a changed DHCP gateway leaves the INET default pointing at `192.168.255.1`.

## Saved GraphQL data never updates in the documented rollout

**Confirmed.** The new data contract is stored in the `GRAPHQL_QUERY` constant at `jobs/gc_bootstrap/__init__.py:59-258`, but the database object is changed only inside `GCBootstrap.run()` at `jobs/gc_bootstrap/__init__.py:336-344`. Syncing the Git repository updates the job definition, not the saved `sp_demo_lab_golden_config` query. The live saved query was inspected during review and is still the old shape, which proves that an explicit job run is required.

The rollout goes directly from repository sync and Design Builder to intended generation at `/home/ubuntu/demo-blog/part5-servers-vrf-internet-border1-nat.md:390-395`. That generation will use the old saved query. The new templates either lack required top-level values or skip the new behavior, depending on how the aggregation result treats missing fields. Run Design Builder first so the `nat-source` tag exists, then run the updated Golden Config bootstrap job before generating intended configuration. The tag ordering matters because Nautobot rejects a GraphQL tag filter whose named tag does not exist.

## Reverse routes resolve through the leaf's own SVI address

**Likely.** Each reverse service record stores `address.address` as `gateway` at `golden-config/templates/eos/static_routes.j2:12`, then renders that address as the static next hop at `golden-config/templates/eos/static_routes.j2:41-43`. For Vlan100 this becomes `ip route 192.168.100.0/24 egress-vrf SERVERS Vlan 100 192.168.100.1`, even though `192.168.100.1` is the same leaf's anycast SVI address.

The canary evidence does not resolve the forwarding risk. Its source and return destination were `192.168.100.1` at `/home/ubuntu/demo-blog/part5-servers-vrf-internet-border1-nat.md:320-335`, so return traffic legitimately terminated on the leaf. The article also states that no K3s VM was tested at `/home/ubuntu/demo-blog/part5-servers-vrf-internet-border1-nat.md:384`. Replace this with an EOS-supported inter-VRF form that performs connected destination forwarding in SERVERS, then verify a host address other than the SVI gateway before treating the reverse path as production intent.

## Policy movement can leave stale native state

**Likely.** The Arista device template emits `tags` only when a device is currently in `origin_devices` at `jobs/sp_demo_lab/designs/0002_devices.yaml.j2:61-64`; there is no `tags: []` branch. Removing a leaf from the origin list therefore does not express removal of `internet-egress-origin` to `create_or_update`.

The same asymmetry affects BORDER1. Selected interfaces receive `NAT Inside` or `NAT Outside` and the DHCP custom field at `jobs/sp_demo_lab/designs/0002_devices.yaml.j2:38-46`, while all other interfaces receive only status and type at lines 47-50. Moving the outside interface or changing the edge device can leave the old role and `ip_address_mode` in Nautobot. `golden-config/templates/ios/nat.j2:4-8` and `golden-config/templates/ios/static_routes.j2:4-8` scan retained roles without enforcing uniqueness, so an old outside role can drive a stale interface choice. Declare empty tags, null roles, cleared custom fields, and removed VRF assignments for non-selected objects, or add a reconciliation test that proves the plugin clears omitted values.

## New behavior is rendered but not behaviorally asserted

**Confirmed.** `make ci` passed with 57 tests and `make ci-full` passed with 149 tests during review. The IOS Batfish scenarios contain only the route reflector and PE router at `tests/test_batfish_validate.py:121-124`, so the new BORDER1 NAT, DHCP, default route, and VRF-aware BGP commands never reach that parser. The EOS Batfish set has one DC-A leaf at `tests/test_batfish_validate.py:177-180`, and `egress-vrf` is explicitly accepted as an unmodeled grammar gap in `tests/test_batfish_validate.py:48-57`.

The checked-in tests do not assert DC-B or DC-C renders, exact next-hop counts, disabled endpoint rejection, wrong-peer-group rejection, the exact NAT prefix set, or exclusion of `172.16.0.0/16`. The claim that focused output checks exercised those cases at `/home/ubuntu/demo-blog/part5-servers-vrf-internet-border1-nat.md:367` has no reproducible test or command in the diff. Add focused assertions for these contracts and include `cisco_ios_border_router.yaml` in the IOS Batfish scenarios before describing the cases as validated by repository checks.

## DHCP addressing is coupled to a fixed gateway

**Likely.** The native outside interface is declared with `address_mode: dhcp` at `jobs/sp_demo_lab/context/__init__.py:140-144`, but the default route uses the fixed config-context next hop `192.168.255.1` from `config_contexts/role_border_router.yaml:29-34` through `golden-config/templates/ios/static_routes.j2:19-20`. The relationship is not validated against the acquired lease.

This remains valid only while DHCP always assigns a directly connected address whose gateway is `.1`. Use a DHCP-derived default or model and validate the external subnet and gateway as one contract. At minimum, add a render or pre-deploy check that rejects a fixed next hop not covered by the outside interface's active lease.

## The article says no VRF name is in config context, but `default` is

**Confirmed.** The article says no VRF names are copied into config context at `/home/ubuntu/demo-blog/part5-servers-vrf-internet-border1-nat.md:168`, then shows `egress_vrf: "default"` at lines 177-180. The source contains the same scalar at `config_contexts/role_leaf.yaml:67-75`, and the static-route template consumes it at `golden-config/templates/eos/static_routes.j2:38`. Either describe `default` as an intentional vendor-policy routing-table identifier or derive the egress routing table from a native model.
